## Die wichtigste Regel

> Jede Architekturentscheidung muss nachweislich mindestens eines dieser Ziele verbessern:
>
> **Kreativität · Workflow · Klangqualität · Echtzeitfähigkeit · Stabilität · Erweiterbarkeit · Wartbarkeit · Benutzererlebnis**
>

## Vision

> VibeCore Univers ist kein Musikprogramm.

Es ist ein **modulares kreatives Universum** für elektronische Musikproduktion und Live-Performance.

Jede Komponente dient einem Ziel:

> Den kreativen Fluss des Musikers zu beschleunigen, ohne technische Komplexität sichtbar zu machen.

VibeCore Univers soll nicht einfach Musik produzieren.  
Es soll Menschen inspirieren, **innerhalb von Sekunden Ideen in Musik zu verwandeln**.

---

## Mission

VibeCoreLiv3 ist die schnellste, intuitivste und kreativste **Performance-Groovebox** für elektronische Musik.

- Starten → Musik machen → Kreativen Flow erleben
- Nicht die Anzahl der Features entscheidet über Qualität, sondern die **Geschwindigkeit, mit der musikalische Ideen umgesetzt werden können**
- Die Technologie bleibt unsichtbar — die Musik steht im Mittelpunkt

## Unternehmensphilosophie

### Der kreative Flow ist das eigentliche Produkt

Code dient dem Flow.  
DSP dient dem Flow.  
AI dient dem Flow.  
UI dient dem Flow.

Wenn eine Entscheidung den kreativen Flow verschlechtert, wird sie verworfen.

### Keine Kompromisse bei Qualität

- Keine Demos
- Keine Beispiel-Implementierungen
- Keine vereinfachten Versionen als Endprodukt
- DAW-Niveau als Mindeststandard

### Refactor First

Bestehender Code besitzt **keinen Bestandsschutz**.  
Wenn eine bessere Lösung existiert: Refaktorieren · Vereinfachen · Modularisieren · Ersetzen.  
Niemals um fehlerhaften Code herum entwickeln.

### No Legacy Bias

Historische Entscheidungen sind Referenz — nicht Verpflichtung.  
Jede Aufgabe wird bewertet, als würde VibeCore heute neu entwickelt werden.

## Product DNA

### Das Instrument

VibeCoreLiv3 ist kein Software-Tool — es ist ein **digitales Musikinstrument**.

- Der Benutzer soll vergessen, dass er Software benutzt
- Jede Berührung erzeugt unmittelbar musikalisches Feedback
- Die Technologie bleibt unsichtbar
- Die Musik steht im Mittelpunkt

### Differenzierung

VibeCore ist kein Klon einer bestehenden DAW.  
Jede Funktion muss antworten: *Warum existiert das in keiner anderen Groovebox?*

### Klangphilosophie

- Audioqualität hat höchste Priorität
- Kein Feature rechtfertigt eine Verschlechterung des Signals
- Der charakteristische VibeCore-Sound ist kein Zufall — er ist Architektur

---

## Designprinzipien

### One Touch
Jede Hauptfunktion ist mit **maximal einer Berührung** erreichbar.

### Five Second Rule
Vom App-Start bis zum ersten Sound: **maximal 5 Sekunden**.  
Keine Registrierung. Keine Konfiguration. Keine Tutorials.

### Hardware Feeling
Jede Interaktion muss sich wie professionelle Hardware anfühlen.  
- Keine verschachtelten Menüs
- Keine Dialogfenster
- Keine unnötigen Einstellungen
- Direkte, haptische Reaktion

### Workflow First
Vor jeder Implementierung:
> Führt diese Funktion zu einem schnelleren kreativen Workflow?  
> Falls nein: Nicht implementieren.

### Simplicity Gate
Komplexität gehört ausschließlich ins System — nicht in die Benutzeroberfläche.  
Jeder Bildschirm verfolgt nur einen klaren Zweck.

### One Function — One Control
Ein Regler. Eine Funktion.  
Keine Doppelbelegungen. Keine versteckten Kontexte.

---

## Qualitätsphilosophie

### Implementation First
Standardverhalten: **Implementieren → Kompilieren → Testen → Fixen → Optimieren → Review → Schließen**

Planung erfolgt ausschließlich zur Beseitigung konkreter technischer Blocker.

### Sprint-Disziplin
Während der Entwicklung eines Features werden keine neuen Anforderungen hinzugefügt.  
Neue Ideen: dokumentieren, nächstem Sprint zuordnen.

### Continuous Review
Nach jedem abgeschlossenen Feature automatisch:  
Architektur · Audio · DSP · Workflow · UI · AI · Performance · QA  
Alle Mängel werden **vor Abschluss** behoben.

## Architecture Decision Process

### Definition of Ready (DoR)

Ein Task startet erst wenn **alle** Punkte erfüllt sind:

| Kriterium | Anforderung |
|-----------|-------------|
| Ziel | Eindeutig definiert |
| Module | Betroffene Module bekannt |
| Akzeptanzkriterien | Liegen vor |
| Architekturfragen | Keine kritischen offen |
| Blocker | Keine vorhanden |

### Executive Decision Gate

Vor jeder Freigabe beantwortet das Board:

| Frage | Anforderung |
|-------|-------------|
| Verbessert diese Funktion den kreativen Workflow? | Ja |
| Ist sie deterministisch und echtzeitfähig? | Ja |
| Ist sie mit der Plattformarchitektur kompatibel? | Ja |
| Erhöht sie die Performance oder zumindest nicht deren Kosten? | Ja |
| Ist sie langfristig wartbar und modular erweiterbar? | Ja |
| Unterstützt sie die Vision einer professionellen mobilen Live-Performance-Groovebox? | Ja |
| Kann die Verbesserung gegen die wichtigste Regel nachgewiesen werden? | Ja |

Nur wenn alle Fragen mit **Ja** beantwortet werden können:  
**SUPREMÉ APPROVED – GO FOR IMPLEMENTATION.**
